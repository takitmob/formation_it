Virtualisation

19 octobre 2026 → 15 novembre 2026 · Semaines 13–16 · 52 h prévues

La virtualisation est le socle technique du cloud moderne : elle permet de faire tourner plusieurs serveurs logiques sur une seule machine physique. Ce module te fait passer des VMs classiques (Hyper-V, VMware, Proxmox) aux conteneurs (Docker) et à une première approche de Kubernetes — un continuum que tu retrouveras intégralement dans Azure.

Objectifs de compétences du module
  • Expliquer les différences entre hyperviseurs de type 1 et type 2
  • Installer et configurer Hyper-V, avec switches virtuels et points de contrôle
  • Comparer objectivement Hyper-V, VMware et Proxmox selon un contexte donné
  • Déployer des conteneurs Docker et les orchestrer avec Docker Compose
  • Comprendre les concepts de base de Kubernetes (pods, cluster, scaling)

Prérequis & matériel

Modules 2 et 3 recommandés (tu vas virtualiser des VMs Windows et Linux). Ton poste doit supporter la virtualisation imbriquée (nested virtualization) si tu utilises déjà une VM — sinon utilise directement ton MacBook comme hôte.

13.1 — Qu'est-ce que la virtualisation ?

La virtualisation permet de faire tourner plusieurs systèmes d'exploitation isolés sur une même machine physique, chacun croyant disposer de son propre matériel dédié. Bénéfices majeurs : consolidation (moins de serveurs physiques, moins de coûts), isolation (une VM plantée n'affecte pas les autres), et agilité (créer, cloner ou supprimer une VM en quelques minutes, snapshots pour revenir en arrière).

13.3 — Composants virtuels d'une VM

  • vCPU — cœurs de processeur virtuels alloués à la VM
  • vRAM — mémoire vive allouée
  • Disque virtuel — fichier représentant le disque dur (VHDX pour Hyper-V, VMDK pour VMware)
  • Carte réseau virtuelle (vNIC) — connectée à un switch virtuel
📁 Étude de cas — PME

Consolidation de 3 serveurs physiques en un seul hôte

Contexte : Le cabinet comptable (suivi depuis le Module 1) possède 3 vieux serveurs physiques distincts : le contrôleur de domaine, le serveur de fichiers, et le serveur applicatif Linux. Coûts de maintenance et d'électricité élevés.

Solution retenue : un seul serveur physique performant avec Hyper-V (type 1), hébergeant les 3 rôles comme VMs distinctes. Chaque VM garde son isolation logique (si une plante, les autres continuent), tout en réduisant le matériel physique de 3 à 1.

Bénéfice concret : possibilité de prendre des points de contrôle avant chaque mise à jour risquée, et de restaurer une VM en quelques minutes en cas de problème — impossible avec du matériel physique seul.

Laboratoire guidé 1 — Installation Hyper-V sur Windows Server

Outil : la VM Windows Server du Module 2 · Durée : 30 min
  1. Dans Server Manager, ajoute le rôle Hyper-V.
  2. Sélectionne la carte réseau à utiliser pour le switch virtuel externe pendant l'assistant.
  3. Redémarre le serveur pour finaliser l'installation.
  4. Ouvre le Gestionnaire Hyper-V et vérifie que le rôle est actif.

Laboratoire guidé 2 — Création d'un switch virtuel

Outil : Gestionnaire Hyper-V · Durée : 20 min
  1. Ouvre le Gestionnaire de commutateurs virtuels.
  2. Crée un switch Externe (accès réseau physique) pour les VMs devant sortir sur le réseau.
  3. Crée un switch Interne (communication VM ↔ hôte uniquement, pas d'accès externe).
  4. Crée un switch Privé (communication VM ↔ VM uniquement, isolé de tout).
  5. Associe chaque type à un cas d'usage réel (ex. Privé pour un labo de test isolé).

Laboratoire guidé 3 — Migration de VM (Live Migration)

Outil : 2 hôtes Hyper-V (ou simulation) · Durée : 35 min
  1. Configure deux hôtes Hyper-V dans le même domaine (ou simule le concept si un seul hôte disponible).
  2. Active la Live Migration dans les paramètres Hyper-V de chaque hôte.
  3. Lance une migration à chaud d'une VM en service vers l'autre hôte.
  4. Observe la continuité de service (ping continu vers la VM pendant la migration).

14.1 — Créer et gérer une VM Hyper-V

La création d'une VM implique de définir : génération (1 = BIOS legacy, 2 = UEFI moderne, recommandée pour Windows/Linux récents), quantité de vCPU et vRAM (statique ou dynamique), taille et type de disque virtuel (à taille fixe = performance, dynamique = économie d'espace), et switch réseau à associer.

14.2 — Points de contrôle (checkpoints)

Point de contrôle standard

Capture l'état complet de la VM (disque, mémoire, configuration) à un instant T. Pratique pour tester une mise à jour risquée, mais déconseillé en production continue — accumule des fichiers différentiels qui dégradent les performances dans la durée.

Point de contrôle de production

Utilise la technologie VSS (Volume Shadow Copy) pour une capture cohérente sans capturer l'état mémoire — plus sûr pour des VMs de production car sans risque d'incohérence applicative à la restauration.

14.3 — VMware et Proxmox : premières installations

VMware ESXi (gratuit en version limitée) est l'hyperviseur type 1 historique du marché entreprise. Proxmox VE est une alternative open source et gratuite, de plus en plus adoptée par les PME cherchant à éviter les coûts de licence VMware — elle intègre nativement la gestion de conteneurs LXC en plus des VMs classiques.

📁 Étude de cas — Hôtel

Isolation d'un service par VM (suite du Module 2)

Contexte : La chaîne hôtelière veut isoler chaque service applicatif (réservation, PMS, Wi-Fi invités) dans sa propre VM sur l'hôte Hyper-V déjà en place.

Points de contrôle : avant chaque mise à jour du logiciel de réservation, un point de contrôle de production est pris automatiquement (tâche planifiée), permettant un retour arrière en quelques minutes en cas de problème, sans affecter les autres VMs.

  4. Configure le type de point de contrôle par défaut de la VM (Production vs Standard).

Il n'y a pas de "meilleur" hyperviseur dans l'absolu — le bon choix dépend de l'écosystème existant, du budget, et des compétences internes. C'est un raisonnement que tu retrouveras identique pour choisir entre Azure, AWS et GCP.

15.2 — Haute disponibilité VM

Cluster de basculement (Failover Cluster)

Plusieurs hôtes physiques regroupés logiquement : si un hôte tombe en panne, les VMs qu'il hébergeait redémarrent automatiquement sur un autre hôte du cluster, avec une interruption minimale.

Prérequis typiques : stockage partagé (SAN, ou Storage Spaces Direct), réseau dédié entre les nœuds, et au minimum 2 hôtes.

15.3 — Introduction à Docker : conteneurs vs VMs

Fig. 15.1 — VMs (isolation forte, lourdes) vs conteneurs (légers, partagent le noyau hôte)

Image Docker

Modèle en lecture seule décrivant un environnement applicatif complet (code, dépendances, configuration), construit à partir d'un Dockerfile. Un conteneur est une instance en cours d'exécution de cette image.

📁 Étude de cas — Usine

Cluster haute disponibilité pour la VM SCADA critique

Contexte : L'usine (suivie depuis les Modules 1 et 2) héberge sa VM de supervision SCADA critique sur un seul hôte Hyper-V — point de défaillance unique inacceptable pour une ligne de production.

Solution retenue : un cluster de basculement à 2 nœuds avec stockage partagé. En cas de panne matérielle d'un hôte, la VM SCADA redémarre automatiquement sur le second nœud en quelques minutes — un compromis pragmatique entre coût et disponibilité, sans nécessiter la complexité d'une solution "zéro interruption".

16.1 — Docker Compose

Docker Compose permet de définir et lancer une application composée de plusieurs conteneurs (ex. un site web + une base de données) à partir d'un seul fichier docker-compose.yml.

version: "3.9"
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: motdepasse

Une seule commande docker compose up -d démarre l'ensemble de la pile applicative.

16.2 — Introduction à Kubernetes

Kubernetes (K8s) orchestre des conteneurs à grande échelle, sur plusieurs machines — Docker Compose reste local à une seule machine, Kubernetes gère un cluster entier avec haute disponibilité, mise à l'échelle automatique et auto-réparation.

Fig. 16.1 — Architecture simplifiée d'un cluster Kubernetes : control plane + nœuds workers exécutant des pods

Pod

Plus petite unité déployable dans Kubernetes — regroupe un ou plusieurs conteneurs partageant le même réseau et stockage.

Scaling automatique

Kubernetes peut ajouter ou retirer des instances de pods automatiquement selon la charge (CPU, mémoire), garantissant la disponibilité pendant les pics de trafic sans intervention manuelle.

Minikube permet de faire tourner un cluster Kubernetes complet à échelle réduite sur ton propre poste, idéal pour apprendre sans infrastructure cloud.

📁 Étude de cas — Administration publique

Modernisation d'une application legacy avec des conteneurs

Contexte : La mairie (suivie depuis les Modules 1 et 3) souhaite moderniser une vieille application de gestion des demandes citoyennes, actuellement installée manuellement sur un serveur physique fragile.

Solution retenue : conteneurisation de l'application avec Docker (une image reproductible, versionnée), orchestrée via Docker Compose pour l'instant (volume raisonnable). Kubernetes est identifié comme évolution future si le volume de demandes citoyennes justifie un besoin de scaling automatique.

Bénéfice concret : déploiement reproductible en quelques minutes sur n'importe quelle machine, fini les "ça marche sur mon poste mais pas en prod" liés aux différences d'environnement.

Laboratoire guidé — Orchestration simple avec Docker Compose

Outil : la VM Linux du Module 3 · Durée : 35 min

  3. Lance la pile : docker compose up -d.
  4. Vérifie que les deux conteneurs tournent : docker compose ps.
  5. Arrête proprement la pile : docker compose down.

Laboratoire guidé — Introduction à Kubernetes (Minikube)

Outil : Minikube (gratuit) · Durée : 40 min
  1. Installe Minikube et démarre un cluster local : minikube start.
  2. Déploie une première application : kubectl create deployment demo --image=nginx.
  3. Expose-la : kubectl expose deployment demo --port=80 --type=NodePort.
  4. Liste les pods créés : kubectl get pods.
  5. Teste le scaling : kubectl scale deployment demo --replicas=3 puis revérifie kubectl get pods.

  4. Documente la procédure de restauration pour ton portfolio.

Quiz de validation — Semaine 16

4 questions
1. À quoi sert Docker Compose ?
Docker Compose démarre toute une pile applicative (plusieurs conteneurs liés) en une seule commande.
2. Quelle est la plus petite unité déployable dans Kubernetes ?
Un pod regroupe un ou plusieurs conteneurs partageant réseau et stockage — c'est l'unité de base de Kubernetes.
3. Quelle différence majeure entre Docker Compose et Kubernetes ?
Kubernetes gère un cluster multi-machines avec scaling automatique ; Compose orchestre localement, sur une seule machine.
4. Dans l'étude de cas de la mairie, pourquoi choisir Docker Compose plutôt que Kubernetes pour l'instant ?
Adopter la complexité de Kubernetes seulement quand le besoin réel (scaling, volume) le justifie est une bonne pratique d'ingénierie.
