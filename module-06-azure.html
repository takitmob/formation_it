Azure

14 décembre 2026 → 10 janvier 2027 · Semaines 21–24 · 52 h prévues

Azure est le point de convergence de tout ce que tu as appris jusqu'ici : réseaux, virtualisation, identités M365 — tout se retrouve sous forme de services cloud managés. Ce module te prépare directement à la certification AZ-104 (Azure Administrator).

Objectifs de compétences du module
  • Naviguer la hiérarchie Azure (groupes de gestion, abonnements, groupes de ressources)
  • Configurer RBAC, réseaux virtuels et stockage Azure
  • Déployer et gérer des machines virtuelles et leur disponibilité
  • Appliquer une gouvernance (Policy, coûts) et déployer via l'infrastructure as code (ARM/Bicep)
  • Connecter Azure AD Connect pour un scénario hybride

Prérequis & matériel

Modules 1 (réseaux), 2 (AD) et 5 (Entra ID) fortement recommandés. Crée un compte Azure gratuit (200$ de crédit les 30 premiers jours, plus des services gratuits en continu) — largement suffisant pour tous les labos de ce module si tu penses à supprimer tes ressources après chaque exercice.

21.1 — La hiérarchie Azure

Fig. 21.1 — Hiérarchie Azure : tenant → groupes de gestion → abonnements → groupes de ressources

Groupe de ressources

Conteneur logique regroupant des ressources liées (VM, réseau, disque) qui partagent le même cycle de vie — supprimer le groupe supprime tout son contenu. C'est l'unité d'organisation de base au quotidien.

Abonnement

Unité de facturation et de limite de quota — une entreprise peut avoir plusieurs abonnements (ex. Production, Développement, Test) pour isoler coûts et permissions.

21.2 — RBAC (Role-Based Access Control)

RBAC attribue des permissions via des rôles (Lecteur, Contributeur, Propriétaire, ou rôles personnalisés) à une portée donnée (groupe de gestion, abonnement, groupe de ressources, ou ressource individuelle) — même logique de moindre privilège que la délégation AD (Module 2).

RôlePermissions
LecteurConsultation uniquement, aucune modification
ContributeurCréer et gérer des ressources, mais pas gérer les accès
PropriétaireContrôle total, y compris la gestion des accès RBAC

21.3 — Régions et zones de disponibilité

Azure opère des régions (datacenters géographiques, ex. France Centre) composées de zones de disponibilité (datacenters physiquement séparés au sein d'une région) — déployer sur plusieurs zones protège contre une panne localisée sans le coût d'une réplication inter-régions.

📁 Étude de cas — PME

Premier abonnement Azure du cabinet comptable

Contexte : Le cabinet comptable (suivi depuis les Modules 1, 2 et 3) veut migrer progressivement certains services vers Azure, en commençant petit.

Structure retenue : un seul abonnement pour l'instant, avec deux groupes de ressources distincts : RG-Production et RG-Test. Le comptable stagiaire reçoit le rôle Lecteur sur l'abonnement (visibilité uniquement), tandis que l'administrateur IT externe reçoit Contributeur limité au groupe Test pour expérimenter sans risque sur la production.

Laboratoire guidé 1 — Création d'un groupe de ressources

  3. Ajoute un tag Environnement=Formation pour t'entraîner à la gestion par étiquettes.
  4. Vérifie sa création dans la liste des groupes de ressources.

Laboratoire guidé 2 — Configuration RBAC (contrôle d'accès)

Outil : Portail Azure · Durée : 25 min

  2. Ajoute une attribution de rôle "Lecteur" à un utilisateur de test.
  3. Vérifie via "Vérifier l'accès" que l'utilisateur a bien les permissions attendues.
  4. Explore la différence entre rôle intégré et rôle personnalisé (sans en créer).

Laboratoire guidé 3 — Création d'un réseau virtuel et sous-réseaux

Outil : Portail Azure · Durée : 30 min
  1. Crée un réseau virtuel (VNet) VNet-Formation avec l'espace d'adressage 10.20.0.0/16.
  2. Crée deux sous-réseaux : subnet-app (10.20.1.0/24) et subnet-data (10.20.2.0/24) — réutilise la méthode de subnetting du Module 1.
  3. Vérifie la configuration dans l'onglet Sous-réseaux du VNet.

22.1 — Réseau virtuel Azure (VNet) approfondi

Un VNet est l'équivalent cloud du réseau local (Module 1) : il définit un espace d'adressage privé, peut être segmenté en sous-réseaux, et connecté à d'autres VNets (peering) ou à un réseau on-premises (VPN Gateway, ExpressRoute).

22.2 — NSG (Network Security Group)

NSG

Équivalent Azure des ACL de pare-feu (Module 1) : liste de règles autorisant ou refusant du trafic entrant/sortant, appliquée à un sous-réseau ou à une interface réseau spécifique. Les règles sont évaluées par ordre de priorité numérique (la plus basse en premier).

22.3 — Déploiement d'une VM Azure

Une VM Azure combine : une image (Windows ou Linux, Marketplace ou personnalisée), une taille (SKU définissant vCPU/RAM), un disque managé, une carte réseau connectée à un sous-réseau, et optionnellement une IP publique.

22.4 — Stockage Azure : Blob et Files

  • Blob Storage — stockage d'objets non structurés (fichiers, images, sauvegardes), avec niveaux d'accès (Chaud/Froid/Archive) pour optimiser les coûts selon la fréquence d'accès
  • Azure Files — partages de fichiers SMB accessibles comme un lecteur réseau classique, montable depuis Windows ou Linux — équivalent cloud du DFS vu au Module 2
📁 Étude de cas — Hôtel

Migration du stockage de photos et documents vers Azure Blob

Contexte : La chaîne hôtelière (suivie depuis les Modules 2, 4 et 5) stocke des milliers de photos de chambres et documents contractuels sur des disques locaux vieillissants.

Solution retenue : migration vers Azure Blob Storage avec gestion automatique des niveaux — les photos actives (moins de 90 jours) restent en niveau Chaud, les documents contractuels de plus de 2 ans basculent automatiquement en niveau Archive (coût très réduit, restauration en quelques heures si besoin).

Laboratoire guidé — Configuration d'un NSG (Network Security Group)

Outil : Portail Azure · Durée : 25 min
  1. Crée un NSG NSG-Formation.
  2. Ajoute une règle entrante autorisant le RDP (port 3389) uniquement depuis ton IP publique.
  3. Ajoute une règle refusant tout autre trafic entrant (priorité plus élevée en numéro = évaluée après).
  4. Associe le NSG au sous-réseau subnet-app créé en semaine 21.

Laboratoire guidé — Déploiement d'une VM Windows/Linux Azure

Outil : Portail Azure · Durée : 30 min
  1. Crée une VM (taille B1s, éligible au niveau gratuit) dans le groupe de ressources de formation.
  2. Associe-la au VNet et sous-réseau créés en semaine 21.
  3. Connecte-toi via RDP (Windows) ou SSH (Linux).
  4. Important : supprime la VM après le test pour ne pas consommer inutilement ton crédit gratuit.

Laboratoire guidé — Configuration du stockage Azure (Blob, Files)

Outil : Portail Azure · Durée : 25 min
  1. Crée un compte de stockage.
  2. Crée un conteneur Blob et téléverse un fichier de test.
  3. Change son niveau d'accès de Chaud à Froid et observe l'impact sur le coût estimé.
  4. Crée un partage Azure Files et monte-le depuis ta VM ou ton poste local.

23.1 — Azure Load Balancer

Répartit le trafic réseau entrant entre plusieurs VMs, avec des sondes d'intégrité qui détectent automatiquement une VM défaillante et cessent de lui envoyer du trafic — principe similaire au basculement DHCP (Module 2), appliqué ici à la répartition de charge web.

23.2 — Azure Backup

Service managé de sauvegarde des VMs, avec planification automatique, rétention configurable, et restauration granulaire (fichier unique ou VM complète) — l'équivalent cloud de Windows Server Backup (Module 2), sans gérer l'infrastructure de stockage sous-jacente.

23.3 — Azure Monitor et alertes

Azure Monitor

Collecte des métriques (CPU, mémoire, disque, réseau) et des journaux de toutes les ressources Azure, avec la possibilité de créer des règles d'alerte déclenchant une notification (email, SMS) ou une action automatisée (redémarrage, scaling) selon des seuils définis.

C'est la continuité directe de Perfmon et de l'Observateur d'événements (Module 2), mais centralisée pour toutes les ressources cloud, avec des tableaux de bord visuels.

📁 Étude de cas — Usine

Haute disponibilité pour le portail de suivi de production

Contexte : L'usine (suivie depuis les Modules 1, 2, 3 et 4) migre son portail web de suivi de production vers Azure, avec une exigence de disponibilité continue pendant les heures de production.

Architecture retenue : deux VMs identiques derrière un Azure Load Balancer, avec Azure Backup planifiant une sauvegarde quotidienne à 3h du matin (hors production), et une alerte Azure Monitor déclenchée si le CPU moyen dépasse 80% pendant plus de 10 minutes — permettant d'anticiper un besoin de scaling avant la saturation.

Laboratoire guidé — Configuration d'Azure Load Balancer

Outil : Portail Azure · Durée : 35 min
  1. Déploie deux petites VMs identiques (ou réutilise-en une existante + une nouvelle).
  2. Crée un Load Balancer public avec une règle de répartition sur le port 80.
  3. Configure une sonde d'intégrité HTTP.
  4. Teste l'accès via l'IP publique du Load Balancer et observe la répartition.
  5. Nettoie toutes les ressources créées après le test.

Laboratoire guidé — Mise en place d'Azure Backup

Outil : Portail Azure · Durée : 25 min
  1. Crée un coffre de sauvegarde (Recovery Services Vault).
  2. Configure une stratégie de sauvegarde quotidienne avec rétention de 30 jours.
  3. Associe une VM de test à cette stratégie.
  4. Lance une sauvegarde immédiate pour valider le fonctionnement.

Laboratoire guidé — Configuration d'Azure Monitor et alertes

Outil : Portail Azure · Durée : 25 min
  1. Ouvre Azure Monitor et consulte les métriques d'une VM de test.
  2. Crée une règle d'alerte : CPU moyen > 80% pendant 10 minutes.
  3. Configure un groupe d'actions envoyant un email de notification.
  4. Documente la configuration pour ton portfolio.

24.1 — Azure Policy

Azure Policy

Règles de conformité appliquées automatiquement aux ressources (ex. "toutes les VMs doivent être dans la région France Centre", "un tag Environnement est obligatoire"). Contrairement à RBAC qui contrôle qui peut faire quoi, Policy contrôle ce qui est autorisé, indépendamment de l'utilisateur.

24.2 — Infrastructure as Code : ARM et Bicep

Plutôt que créer des ressources manuellement dans le portail, on peut les décrire dans un fichier et les déployer de façon reproductible :

  • Templates ARM (Azure Resource Manager) — format JSON natif d'Azure, verbeux mais universel
  • Bicep — langage plus lisible qui se compile vers ARM, adopté comme standard moderne recommandé par Microsoft
// Exemple Bicep simplifié : un groupe de ressources avec un compte de stockage
resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'stformationcabinet'
  location: 'francecentral'
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}

L'avantage majeur : la même infrastructure peut être recréée identique à l'identique en environnement de test, de préproduction et de production — fini les différences de configuration invisibles entre environnements.

24.3 — Azure AD Connect (scénario hybride)

Synchronise les comptes d'un AD DS local (Module 2) vers Entra ID, permettant une identité unique pour l'utilisateur, que ce soit pour se connecter au domaine local ou à M365/Azure — le pont entre l'infrastructure historique et le cloud.

24.4 — Gestion des coûts

Azure Cost Management permet de suivre les dépenses en temps réel, définir des budgets avec alertes, et identifier les ressources sous-utilisées (VM allumée en permanence mais peu sollicitée, disque orphelin non attaché) — une compétence directement rentable pour toute organisation.

📁 Étude de cas — Bilan du module

Gouvernance complète pour le cabinet comptable

Bilan : Le cabinet comptable dispose maintenant d'une infrastructure Azure gouvernée : Azure Policy impose la région et le tagging, l'infrastructure est déployée via Bicep pour garantir la reproductibilité, Azure AD Connect synchronise les identités avec l'AD local existant, et un budget mensuel avec alerte à 80% évite les mauvaises surprises de facturation.
