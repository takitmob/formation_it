PowerShell est le langage d'automatisation natif de l'écosystème Microsoft — Windows Server, Active Directory, M365 et Azure se pilotent tous avec les mêmes cmdlets. Ce module transforme les tâches manuelles répétitives des modules précédents en scripts fiables et réutilisables.

  • Créer des modules personnalisés et automatiser des rapports
  • Interagir avec l'API Microsoft Graph pour piloter M365/Azure

25.1 — La logique Verbe-Nom

Toutes les cmdlets PowerShell suivent la convention Verbe-Nom : Get-Process, Set-Content, New-Item, Remove-Item. Cette cohérence rend PowerShell prévisible — une fois la logique comprise, on devine souvent le nom d'une cmdlet.

VerbeAction
GetRécupérer une information
SetModifier une propriété existante
NewCréer un nouvel objet
RemoveSupprimer

25.2 — Le pipeline : objets, pas texte

Contrairement à Bash (Module 3) qui fait circuler du texte entre les commandes, PowerShell fait circuler de véritables objets .NET avec leurs propriétés — un avantage majeur pour manipuler des données structurées sans parsing fragile.

25.3 — Filtrage et tri

Get-Service | Where-Object Status -eq "Running"
Get-ADUser -Filter * | Sort-Object Surname
Get-Process | Select-Object Name, CPU, Id -First 5

25.4 — Gestion des utilisateurs AD via PowerShell

Tout ce que tu as fait manuellement en Module 2 (créer des utilisateurs, des OU, des groupes) devient scriptable et reproductible :

Get-ADUser -Filter * -SearchBase "OU=Comptabilite,DC=cabinet,DC=local"
New-ADUser -Name "Marie Dubois" -SamAccountName "marie.dubois" -Enabled $true

26.1 — Variables, tableaux et boucles

$nom = "Marie"                      # variable simple
$utilisateurs = @("jean", "marie", "paul")   # tableau

foreach ($u in $utilisateurs) {
    Write-Host "Traitement de $u"
}

$i = 0
while ($i -lt 5) {
    Write-Host "Compteur : $i"
    $i++
}

26.2 — Fonctions réutilisables

function Get-DiskSpaceReport {
    param(
        [string]$ComputerName = "localhost"
    )
    Get-PSDrive -PSProvider FileSystem | Select-Object Name, Used, Free
}

Get-DiskSpaceReport

Une fonction bien conçue accepte des paramètres (comme $ComputerName ci-dessus) pour rester réutilisable dans différents contextes, plutôt que de coder des valeurs en dur.

26.3 — Gestion des erreurs (Try/Catch)

try {
    Get-ADUser -Identity "utilisateur_inexistant" -ErrorAction Stop
} catch {
    Write-Warning "Utilisateur introuvable : $($_.Exception.Message)"
} finally {
    Write-Host "Traitement terminé"
}

Sans gestion d'erreur, un script s'arrête brutalement ou pire, continue silencieusement avec des données incorrectes. Try/Catch/Finally permet de réagir proprement et de garder une trace claire de ce qui s'est passé.

26.4 — PowerShell Remoting

PowerShell Remoting (WinRM)

Permet d'exécuter des commandes sur un ou plusieurs serveurs distants comme si tu étais connecté localement, via le protocole WinRM. Fondation de l'administration à grande échelle : plus besoin de se connecter serveur par serveur.

Invoke-Command -ComputerName SRV01,SRV02 -ScriptBlock { Get-Service | Where-Object Status -eq "Stopped" }
📁 Étude de cas — Hôtel

Script de vérification de santé multi-serveurs

Contexte : La chaîne hôtelière (suivie depuis les Modules 2, 4, 5 et 6) possède plusieurs serveurs Windows répartis sur ses 3 établissements et veut un contrôle de santé quotidien centralisé.

27.1 — Automatisation de rapports

Get-Process | Sort-Object CPU -Descending | Select-Object -First 10 |
    ConvertTo-Html -Title "Rapport CPU" | Out-File rapport.html

Get-ADUser -Filter * -Properties LastLogonDate |
    Select-Object Name, LastLogonDate |
    Export-Csv derniere_connexion.csv -NoTypeInformation -Encoding UTF8

Combiner cmdlets et export permet de générer automatiquement des rapports réguliers (via une tâche planifiée) sans intervention manuelle.

27.2 — Gestion des services Windows via script

Get-Service -Name "Spooler" | Restart-Service
Get-Service | Where-Object {$_.Status -eq "Stopped" -and $_.StartType -eq "Automatic"} |
    Start-Service

Ce dernier exemple illustre un cas très courant en administration : redémarrer automatiquement tout service configuré en démarrage automatique mais actuellement arrêté — un filet de sécurité simple contre les plantages silencieux.

27.3 — Interaction avec Microsoft Graph

Microsoft Graph

API unifiée permettant de piloter par script l'ensemble des services M365 et Entra ID (utilisateurs, emails, calendriers, Teams, licences) — le module PowerShell Microsoft.Graph en est le point d'entrée natif.

Connect-MgGraph -Scopes "User.Read.All"
Get-MgUser -Filter "department eq 'Comptabilite'"

C'est le pont direct entre les compétences PowerShell de ce module et l'administration M365 vue au Module 5 — la même logique de script s'applique, cette fois au cloud plutôt qu'à l'AD local.

28.1 — Créer un module PowerShell personnalisé

Un module (fichier .psm1) regroupe plusieurs fonctions réutilisables dans un package importable — l'équivalent PowerShell d'une bibliothèque Python (Module 8) ou d'un package Docker (Module 4).

# MonModule.psm1
function Get-DiskSpaceReport { ... }
function New-BulkADUser { ... }
Export-ModuleMember -Function Get-DiskSpaceReport, New-BulkADUser
Import-Module .\MonModule.psm1
Get-DiskSpaceReport

28.2 — Script de provisionnement automatisé

Combine tout ce que tu as appris : création d'une VM Azure (Module 6) ou Hyper-V (Module 4) pilotée entièrement par script, avec configuration post-déploiement (installation de rôles, jonction au domaine) — l'équivalent PowerShell de l'infrastructure as code Bicep vue au Module 6.

28.3 — Planification de tâches (Task Scheduler)

$action = New-ScheduledTaskAction -Execute "PowerShell.exe" -Argument "-File C:\Scripts\rapport.ps1"
$trigger = New-ScheduledTaskTrigger -Daily -At "06:00"
Register-ScheduledTask -TaskName "RapportQuotidien" -Action $action -Trigger $trigger

C'est l'équivalent Windows de cron (Module 3) — la logique de planification est la même, la syntaxe diffère.
