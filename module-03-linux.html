Linux

21 septembre 2026 → 18 octobre 2026 · Semaines 9–12 · 52 h prévues

Linux fait tourner la majorité des serveurs web, des infrastructures cloud et des systèmes embarqués dans le monde. Ce module te rend autonome en ligne de commande : navigation, permissions, gestion de services, et automatisation par scripts — des compétences directement transférables à Azure et au module Python.

Objectifs de compétences du module
  • Naviguer et administrer un système Linux entièrement en ligne de commande
  • Gérer utilisateurs, groupes et permissions selon le principe du moindre privilège
  • Administrer les services avec systemd et diagnostiquer via les logs
  • Sécuriser un accès SSH et un serveur web
  • Écrire des scripts Bash pour automatiser des tâches récurrentes

Prérequis & matériel

Aucun prérequis Linux. Tu auras besoin d'une VM (VirtualBox ou Hyper-V, déjà utilisé au Module 2) avec Ubuntu Server LTS (gratuit). Un terminal SSH (Terminal.app sur Mac, ou l'app Termius sur iPhone) sera utile pour t'entraîner même en déplacement.

9.1 — Distributions et philosophie Linux

Linux est un noyau (kernel) open source, distribué avec un ensemble d'outils sous forme de distributions (« distros »). Les plus courantes en entreprise :

  • Famille Debian/Ubuntu — gestionnaire de paquets APT, très répandue sur les serveurs web et le cloud
  • Famille Red Hat (RHEL, CentOS Stream, Rocky Linux, Fedora) — gestionnaire de paquets DNF/YUM, standard en environnement critique/entreprise
  • SUSE — répandue en Europe, notamment sur mainframe et environnements SAP

Ce module utilise Ubuntu Server pour sa simplicité de prise en main, mais les concepts sont transférables à toutes les distributions.

9.2 — L'arborescence de fichiers (FHS)

Fig. 9.1 — Arborescence FHS (Filesystem Hierarchy Standard) simplifiée

Tout est fichier

Principe fondateur d'Unix/Linux : périphériques, processus et flux de données sont représentés comme des fichiers, manipulables avec les mêmes outils standards (cat, redirection, pipes).

9.4 — Gestion des paquets

Sur Ubuntu/Debian, APT (Advanced Package Tool) gère l'installation, la mise à jour et la suppression de logiciels, en résolvant automatiquement les dépendances.

sudo apt update              # rafraîchit la liste des paquets disponibles
sudo apt upgrade             # met à jour les paquets installés
sudo apt install nginx       # installe le paquet nginx
sudo apt remove nginx        # désinstalle nginx

Sur RHEL/Fedora, l'équivalent est DNF (anciennement YUM) : sudo dnf install nginx.

10.1 — Utilisateurs et groupes

Chaque utilisateur Linux possède un identifiant unique (UID) et appartient à un ou plusieurs groupes (GID). Les informations de compte sont stockées dans /etc/passwd (infos publiques) et les mots de passe chiffrés dans /etc/shadow (lisible uniquement par root).

sudo useradd -m -s /bin/bash jdupont   # crée l'utilisateur avec dossier personnel
sudo passwd jdupont                    # définit son mot de passe
sudo usermod -aG sudo jdupont          # ajoute jdupont au groupe sudo
sudo groupadd compta                   # crée un groupe

10.2 — Permissions : rwx et notation octale

Chaque fichier possède trois niveaux de permissions — propriétaire, groupe, autres — chacun avec trois droits possibles : read, write, execute.

Fig. 10.1 — Décomposition des permissions rwx et leur équivalent octal (r=4, w=2, x=1)

chmod 754 script.sh        # rwx pour le propriétaire, r-x pour le groupe, r-- pour les autres
chmod u+x script.sh        # ajoute le droit d'exécution au propriétaire (notation symbolique)
chown jdupont:compta fichier.txt   # change propriétaire et groupe

10.3 — sudo et le moindre privilège

sudo (superuser do)

Permet à un utilisateur autorisé d'exécuter une commande avec les privilèges root, de façon tracée (chaque usage est journalisé) — préférable à une connexion permanente en root. La configuration se fait dans /etc/sudoers (à éditer uniquement avec visudo).

10.4 — Gestion des processus et cron

ps aux              # liste tous les processus en cours
top                 # vue dynamique de l'utilisation CPU/RAM
kill -9 1234        # termine le processus d'ID 1234
crontab -e          # édite les tâches planifiées de l'utilisateur courant

Syntaxe cron : minute heure jour mois jour_semaine commande. Exemple — sauvegarde tous les jours à 2h du matin : 0 2 * * * /home/jdupont/backup.sh.

📁 Étude de cas — Hôtel

Serveur Linux partagé pour le logiciel de réservation

Contexte : L'hôtel (suivi depuis le Module 2) héberge son logiciel de réservation sur un serveur Linux partagé entre la réception et la direction, chacun avec des besoins d'accès différents.

11.1 — systemd et la gestion des services

systemd est le système d'initialisation utilisé par la quasi-totalité des distributions modernes. Il démarre, arrête et surveille les services (appelés « units »).

sudo systemctl status nginx     # état actuel du service
sudo systemctl start nginx      # démarre le service
sudo systemctl enable nginx     # active le démarrage automatique au boot
sudo systemctl restart nginx    # redémarre le service

11.2 — Logs avec journalctl

systemd centralise les journaux via journald, consultables avec journalctl :

journalctl -u nginx --since today   # logs du service nginx depuis aujourd'hui
journalctl -p err                   # uniquement les erreurs
journalctl -f                       # suivi en temps réel (comme "tail -f")

11.3 — Sécuriser l'accès SSH

Par défaut, SSH accepte l'authentification par mot de passe — vulnérable au brute-force. La bonne pratique est l'authentification par clé :

  1. Génère une paire de clés sur ton poste : ssh-keygen -t ed25519
  2. Copie la clé publique sur le serveur : ssh-copy-id user@serveur
  3. Sur le serveur, désactive l'authentification par mot de passe dans /etc/ssh/sshd_config : PasswordAuthentication no
  4. Désactive aussi la connexion root directe : PermitRootLogin no
  5. Redémarre le service : sudo systemctl restart sshd

11.4 — Montage et LVM

LVM (Logical Volume Manager)

Couche d'abstraction entre les disques physiques et les systèmes de fichiers, permettant de redimensionner des volumes à chaud, d'ajouter du stockage sans interruption, et de créer des snapshots.

lsblk                        # liste les disques et partitions
sudo mount /dev/sdb1 /mnt/data   # monte une partition
df -h                         # espace disque utilisé, lisible
📁 Étude de cas — Usine

Serveur Linux embarqué pour la collecte de données capteurs

Contexte : L'usine (suivie depuis le Module 1) déploie un petit serveur Linux embarqué qui collecte en continu les données de capteurs de température sur la ligne de production, avant de les transmettre à un serveur central.

Résilience via systemd : le service de collecte est configuré avec Restart=always dans son fichier unit systemd — en cas de plantage du processus (bug logiciel, coupure momentanée), systemd le relance automatiquement en quelques secondes, sans intervention humaine.

Sécurité : l'accès SSH au boîtier est restreint par clé uniquement, connexion root désactivée, et les logs sont consultés à distance via journalctl pour diagnostiquer sans devoir se déplacer physiquement sur la ligne.

12.1 — Syntaxe Bash de base

#!/bin/bash
NOM="serveur01"                      # variable
if [ -d "/data" ]; then              # condition : le dossier existe ?
  echo "Le dossier existe sur $NOM"
else
  mkdir -p /data
fi

for fichier in /data/*.log; do       # boucle sur les fichiers .log
  echo "Traitement de $fichier"
done

Un script commence toujours par un shebang (#!/bin/bash) qui indique l'interpréteur à utiliser. Il doit être rendu exécutable avec chmod +x script.sh puis lancé avec ./script.sh.

12.2 — Arguments et gestion d'erreurs

#!/bin/bash
set -e   # arrête le script à la première erreur
DOSSIER=$1   # premier argument passé au script

if [ -z "$DOSSIER" ]; then
  echo "Usage: $0 "
  exit 1
fi

12.3 — Analyse de logs avancée

journalctl --since "1 hour ago" -p warning   # avertissements de la dernière heure
grep -i "failed" /var/log/auth.log            # recherche des échecs de connexion
journalctl -u sshd | grep "Invalid user"      # tentatives de connexion invalides

12.4 — SELinux et AppArmor

Ces deux systèmes ajoutent un contrôle d'accès obligatoire (MAC) au-delà des permissions classiques rwx : même un processus root peut être bloqué s'il tente une action non autorisée par sa politique.

  • SELinux — utilisé par défaut sur RHEL/Fedora, politique très granulaire mais plus complexe
  • AppArmor — utilisé par défaut sur Ubuntu/Debian, basé sur des profils par chemin de fichier, plus simple à appréhender
sudo aa-status                # état d'AppArmor et profils actifs
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx   # applique un profil en mode strict
📁 Étude de cas — Administration publique

Sauvegarde automatisée nocturne des dossiers citoyens

Contexte : La mairie (suivie depuis le Module 1) stocke des dossiers citoyens sensibles sur un serveur Linux et doit garantir une sauvegarde fiable, tracée, et conforme aux exigences de protection des données publiques.

Solution : un script Bash exécuté chaque nuit à 1h via cron, qui archive les dossiers, les chiffre avec GPG, transfère l'archive vers un stockage distant, et journalise chaque étape avec horodatage. En cas d'échec (ex. espace disque insuffisant), le script envoie une alerte email avant d'échouer proprement (set -e).

Durcissement : AppArmor confine le processus de sauvegarde pour qu'il ne puisse accéder qu'aux dossiers strictement nécessaires — même si le script était compromis, l'impact resterait limité.
